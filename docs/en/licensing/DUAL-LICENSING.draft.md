# Dual licensing — pending strategy, not a new license

Project author: KUVEXTA GROUP. Prepared 2026-10-27.
[Spanish source](../../../licencias/DOBLE-LICENCIA.borrador.md).

**Inactive.** This document describes a possible commercial strategy. It is not a current choice offered to package recipients.

One possible strategy offers the same code version under an open license and, separately, a commercial license with different permissions. For example, AGPL-3.0-only or a commercial contract. This is only an example: neither branch is selected.

Before offering it, verify that the licensor has sufficient authority over every affected component to make both offers. Dependencies or contributions received under one license do not automatically become dual-licensed. Contribution terms and authorizations must be defined expressly.

The commercial option must specify what it additionally offers: redistribution terms, integration, warranties or support, as applicable. An open license may already permit charging; do not sell as exclusive a permission that the open branch already grants.

If selected, the decision must identify the version, files, both complete licenses and the right to choose. Do not confuse alternative offers (OR, where applicable) with cumulative obligations (AND). Documentation, skill and third-party material licenses are separate decisions.

Later implementation: rights/contributions inventory → branch selection → contract and notices → approval → package with explicit version and licenses. Publishing a new edition does not withdraw previously granted rights.
